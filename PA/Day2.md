# TIL Day 2

## 1. 로봇 소프트웨어 스택의 세 계층

- 인지(Perception)
- 판단(Planning / Decision)
- 제어(Control)

로봇은 인지 → 판단 → 제어가 반복되는 **폐루프(Closed Loop)** 시스템이다.

---

### 1.1 인지(Perception)

센서 원시 데이터를 처리해 현재 상황을 파악한다.

#### 입력
- 카메라 영상
- 라이다 점군
- 가속도
- 각속도

#### 출력
- 장애물이 전방 1.2m에 있다.
- 로봇이 5도 기울었다.

#### 대표 알고리즘
- 객체 검출
- SLAM
- 센서 융합

> **중요한 것은 상태 추정이다.**
>
> 센서는 노이즈가 섞인 원시 데이터이기 때문에 가장 그럴듯한 현재 상태를 계산한다.

---

### 1.2 판단(Planning / Decision)

인지 결과와 목표를 바탕으로 무엇을 할지 결정한다.

#### 입력
- 환경 모델
  - 장애물 지도
  - 내 위치
- 상위 목표
  - "현관까지 이동"

#### 출력
- 경로
- 행동 결정
  - 왼쪽으로 회피
- 속도 프로파일

#### 대표 알고리즘
- 전역 경로 계획
- 지역 경로 계획
- 행동 트리

판단은 보통 **전역(Global)**과 **지역(Local)**으로 나뉜다.

- **전역 계획**: 전체 지도에서 현관까지 가는 길을 계획
- **지역 계획**: 지금 눈앞의 장애물을 어떻게 피할지 결정

전역 계획은 상대적으로 느리게 갱신해도 되지만, 지역 계획은 환경 변화에 대응하기 위해 짧은 주기로 갱신한다.

---

### 1.3 제어(Control)

판단이 정한 목표를 실제 모터 명령으로 바꾼다.

#### 입력
- 목표 속도
- 목표 위치
- 현재 측정값

#### 출력
- 모터 전압
- 모터 전류
- PWM Duty

#### 대표 알고리즘
- PID 제어
- 모델 기반 제어

> 제어 계층의 특징은 **오차를 끊임없이 보정**한다는 것이다.

---

# 2. 데이터는 어떻게 흐를까? — 멀티레이트 구조

세 계층은 독립적으로 존재하지 않고 끊임없이 데이터를 주고받는다.

중요한 점은 계층마다 **데이터가 갱신되는 속도가 다르다**는 것이다.

이를 **멀티레이트(Multi-Rate) 구조**라고 한다.

| 계층 | 전형적 주기 | 주기를 결정하는 요인 |
| --- | --- | --- |
| 제어 | 100Hz ~ 10kHz | 모터·기구의 동역학 |
| 인지 | 10 ~ 60Hz | 센서 프레임률 |
| 판단(지역) | 5 ~ 20Hz | 환경 변화 속도 |
| 판단(전역) | 0.1 ~ 1Hz | 목표·지도의 변화 빈도 |

그렇다면 빠른 제어 루프(1kHz)가 느린 인지 결과(30Hz)를 어떻게 사용할까?

**기다리지 않는다.**

> **핵심 원칙: 빠른 루프는 느린 루프를 기다리지 않는다.**

최악의 경우 시스템이 불안정해질 수 있다.

이러한 설계 실수의 대표적인 예가 다음과 같다.

- 우선순위 역전(Priority Inversion)
- 블로킹(Blocking)

# 3. 실시간성 — 주기, 지연, 지터

## 주기(Period)

작업이 얼마나 자주 반복되는가?

## 지연(Latency)

입력이 들어와서 출력까지 걸리는 시간이다.

## 지터(Jitter)

주기가 얼마나 들쭉날쭉한가를 의미한다.

평균 주기가 같아도 지터가 크면 제어가 불안정해질 수 있다.

따라서 **일정함, 즉 낮은 지터가 중요하다.**

---

## 3.1 지터는 제어를 망가뜨린다

디지털 제어기는 대부분 일정한 주기 `Δt`로 실행된다는 가정 위에서 설계된다.

지터가 커지면

- 적분·미분 계산이 매 주기 달라지고
- 제어 출력에 노이즈가 발생하며
- 심하면 시스템이 진동하거나 발산할 수 있다.

즉 지터는 단순한 **성능 저하**가 아니라 **제어 이론의 전제를 깨뜨릴 수 있는 문제**이다.

모듈 ③에서 PID를 구현할 때 이 감각이 다시 등장한다.

# 4. 실시간성 — Hard, Firm, Soft

실시간성이란 단순히 **빠르다는 것이 아니다.**

정해진 마감 시간(Deadline) 안에 작업을 끝내는 것을 보장한다는 의미이다.

## Hard Real-Time

마감을 넘기는 순간 치명적인 실패가 발생한다.

- 로봇 낙하 방지
- 에어백 전개

## Firm Real-Time

마감을 넘으면 결과의 가치가 0이 되어 폐기한다.

- 화상회의 영상 프레임

## Soft Real-Time

마감을 넘겨도 결과의 가치가 점진적으로 하락한다.

- 로봇 상태 모니터링 대시보드

---

## 4.1 로봇 시스템에 적용

| 작업 | 등급 | 이유 |
| --- | --- | --- |
| 모터 전류/속도 제어 루프 | Hard | 마감 초과 = 제어 불안정·하드웨어 손상 |
| 비상 정지(E-Stop) 처리 | Hard | 마감 초과 = 안전사고 |
| 카메라 프레임 기반 객체 인식 | Firm | 늦은 프레임 결과는 폐기하고 다음 프레임 처리 |
| 지도 갱신·경로 재계획 | Soft | 조금 늦어도 이전 경로로 주행 가능 |
| 로그 업로드·모니터링 | Soft | 지연이 품질에 거의 영향 없음 |

이 분류가 중요한 이유는 **등급에 따라 실행 환경이 달라지기 때문**이다.

# 5. 지터는 어디서 생기고, 어떻게 줄일까?

일반 PC/Linux에서 1ms 주기 루프를 돌려 보면 주기가 미세하게 출렁인다.

원인은 여러 겹이다.

## ① OS 스케줄러

Linux는 기본적으로 공평성을 추구하는 범용 스케줄러이기 때문에, 내 프로세스가 언제 CPU를 받을지 정확히 보장하지 않는다.

## ② 인터럽트·다른 프로세스

네트워크 패킷 처리나 백그라운드 작업이 끼어들 수 있다.

## ③ 캐시 미스·메모리 페이징

같은 코드도 캐시 상태나 메모리 상황에 따라 실행 시간이 달라질 수 있다.

## ④ 동적 메모리 할당·가비지 컬렉션

할당 시간이 일정하지 않을 수 있다.

특히 Python 같은 관리형 언어에서는 이러한 실행 시간 변동을 고려해야 한다.

---

## 5.1 지터를 줄이는 방법

### RTOS(Real-Time OS)

대표적으로 다음과 같은 RTOS가 있다.

- FreeRTOS
- Zephyr

우선순위 기반 선점형 스케줄링을 통해 높은 우선순위의 작업이 먼저 실행되도록 설계할 수 있다.

MCU에서 Hard 실시간을 구현하는 대표적인 방법이다.

### Linux 실시간 패치(PREEMPT_RT)

Linux 커널의 선점 지연을 줄여 실시간 성능을 높일 수 있다.

ROS 2 실시간 노드에서도 활용된다.

### 실시간 코드 작성 수칙

제어 루프 안에서는 다음과 같은 작업을 피하는 것이 좋다.

- 동적 메모리 할당
- 파일 I/O
- 블로킹 통신

대신 실행 시간이 일정한(Deterministic) 알고리즘을 사용하는 것이 중요하다.

# 6. 심화 — WCET와 스케줄링 가능성

## WCET(최악의 경우 실행 시간)

Hard 실시간 시스템 설계에서는 평균이 아니라 **최악의 경우 실행 시간(WCET, Worst-Case Execution Time)**을 따진다.

예를 들어,

```text
보통 실행 시간 : 0.3ms
최악 실행 시간 : 2ms
