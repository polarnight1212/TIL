# SLAM 현장 테스트

## 테스트 구성
- 오늘은 2026-10-26 실제 로봇 테스트를 진행했다
- 서브 로봇은 Raspberry Pi에서 동작했다
- Pi에서 LiDAR 2개 데이터를 병합하고 OpenCR의 바퀴·IMU 데이터를 받았다
- PC에서는 SLAM, EKF, 플래너를 실행했다
- Pi와 PC는 Wi-Fi를 통해 ROS 2로 통신했다
- 노드가 나뉘면 계산을 분산할 수 있지만 네트워크와 컴퓨터 시계가 새로운 입력 조건이 된다

## ROS 2 DDS 탐색
- DDS는 네트워크에서 참가자와 토픽을 서로 찾고 데이터를 전달한다
- 기본 탐색은 멀티캐스트를 사용한다
- Wi-Fi가 붐비거나 장비가 멀티캐스트를 막으면 발견과 데이터 전달이 어긋날 수 있다
- 오늘은 토픽 목록은 보이는데 실제 데이터가 오지 않는 현상을 봤다
- 목록이 보인다는 것만으로 센서 메시지 수신까지 확인된 것은 아니다
- ROS_STATIC_PEERS는 지정한 상대의 참가자를 탐색 대상으로 추가한다
- Fast DDS의 maxInitialPeersRange 기본값은 4였다
- 상대 PC 참가자가 약 4개를 넘으면 일부 참가자를 찾지 못할 수 있었다
- XML 프로파일에서 범위를 30으로 늘려 탐색 문제를 해결했다
- ros2 CLI 명령도 실행할 때마다 새 DDS 참가자를 만든다
- CLI를 반복 실행하는 것 자체가 탐색 트래픽을 만든다는 점을 알았다
- 네트워크가 불안정할 때는 CLI 참가자 수와 실제 데이터 흐름을 함께 봐야 한다

## 컴퓨터 시계와 메시지 시각
- ROS 메시지의 header.stamp는 메시지를 보낸 컴퓨터의 시계를 기준으로 한다
- 서로 다른 컴퓨터의 시계가 어긋나면 메시지의 나이 계산도 어긋난다
- 오늘 Pi 시계는 PC보다 22~48 ms 빨랐다
- 플래너와 제어기는 10 ms를 넘게 미래인 데이터를 버렸다
- 내부 기준은 age >= -0.01인 경우였다
- Pi가 보낸 데이터가 미래 시각으로 판단되어 간헐적인 feedback fault가 났다
- 센서 자체가 끊기지 않아도 시계 차이만으로 입력이 탈락할 수 있다
- chrony를 사용해 Pi가 PC를 시간 서버로 따르게 했다
- 동기화 후 시계 차이는 약 0.1 ms로 줄었다
- 분산 로봇을 실행하기 전에 두 컴퓨터 시계를 확인하는 습관이 필요하다

## TF 시각 문제
- TF는 프레임 사이 변환을 시각과 함께 보관한다
- `extrapolation into the future`는 요청한 시각이 TF 버퍼의 최신 데이터보다 뒤라는 뜻이다
- 즉, 변환을 요청한 시점에 필요한 TF가 아직 도착하지 않았다
- EKF의 transform_time_offset은 TF를 약간 미래 시각으로 발행하게 한다
- 이 오프셋으로 요청 시각과 TF 발행 시각의 차이를 맞춰 경고를 크게 줄였다(완전히 없애지는 못함)
- 장애물 샘플 하나를 처리하지 못했다고 전체 샘플을 버리는 구현은 위험하다
- 한 번의 TF 실패가 센서 입력 전체의 손실로 번지지 않도록 실패 범위를 확인한다

## 센서 방향과 회전 부호
- 센서의 물리적 방향과 소프트웨어가 가정한 방향은 일치해야 한다
- udev 포트 이름이 앞·뒤 LiDAR를 반대로 가리키면 앞쪽 스캔을 뒤쪽으로 해석한다
- 이 경우 로봇에게 앞으로 가라고 해도 실제로는 뒤로 가는 것처럼 보일 수 있다
- IMU가 뒤집혀 있다는 가정으로 roll=π 보정을 넣었지만 그 가정은 틀렸다
- 잘못된 보정은 회전 부호를 반대로 만든다
- EKF가 반대로 회전한다고 오인하면 제어기는 회전을 더 명령할 수 있다
- 부호 오류가 피드백 루프에서 폭주로 커질 수 있다
- 제자리에서 로봇을 회전시키며 바퀴, IMU, SLAM의 부호와 크기를 비교한다
- 부호가 맞는지와 회전량이 서로 비슷한지 둘 다 확인해야 한다
- 오늘 바퀴 회전량은 IMU 회전량의 1.5~1.65배였다
- wheel_separation 설정은 터틀봇 기본값인 0.288 m였다
- 회전량 비율로 역산한 실효 바퀴 간격은 약 0.43 m로, 설정과 달랐다(자로 잰 값은 아님)
- 기본값을 그대로 쓰면 바퀴 기반 회전 추정에 체계적인 오차가 생긴다

## SLAM 갱신과 위치 점프
- slam_toolbox는 이동·회전 조건을 만족할 때 스캔을 처리한다
- 기본 조건은 0.5 m 이동 또는 0.5 rad 회전이었다
- 오늘 주행에서는 실제로 약 9초에 한 번 스캔이 처리됐다
- 처리 간격이 길면 그 사이 오도메트리 오차가 쌓인다
- 다음 스캔 매칭에서 오차를 한꺼번에 보정하면서 위치가 점프한다
- 오늘 보정 때 위치가 15~22 cm 움직이는 점프를 관찰했다
- minimum_time_interval을 0.2로 낮췄다
- 이동 조건도 0.01 m로 바꿨다
- 주행 중에는 약 0.3초 간격, 약 5 Hz로 스캔이 처리됐다
- 더 짧은 간격은 오도메트리 오차가 커지기 전에 보정할 기회를 준다
- 이동 조건은 정지 중 스캔이 계속 쌓이는 것을 막는다
- 시간 조건만으로 계속 처리하면 정지 상태에서도 그래프가 커질 수 있다

## SLAM과 오도메트리의 관계
- slam_toolbox는 스캔 매칭의 초기 추정에 odom->base_link TF를 사용한다
- 바퀴와 IMU는 ekf_local에 들어가 로컬 오도메트리를 만든다
- 따라서 SLAM은 바퀴 정보를 이미 초기 추정으로 활용한다
- SLAM 결과를 바퀴와 함께 다시 ekf_global에 넣으면 같은 정보를 두 번 셀 수 있다
- 표준 구조는 ekf_local이 odom->base_link를 발행하는 형태다
- slam_toolbox는 map->odom 보정을 발행한다
- 로봇의 지도상 위치는 map->odom과 odom->base_link를 합성해 얻는다
- map과 odom을 나누면 연속 이동과 전역 보정을 각자 맡길 수 있다
- EKF는 입력 센서의 공분산, 즉 불확실성에 따라 센서 비율을 정한다
- SLAM 보정 간격이 길면 그동안 오도메트리 불확실성이 커진다
- 이때 보정이 들어오면 위치가 거의 100% SLAM 쪽으로 끌려가며 점프할 수 있다
- 짧은 갱신 주기는 오차가 쌓이는 시간을 줄여 점프를 완화한다

## 휠 오도메트리의 한계
- 엔코더 틱 자체가 정확해도 이동 거리 추정은 정확하다고 단정할 수 없다
- 바퀴 반지름과 바퀴 간격 설정 오차가 회전·이동에 반영된다
- 미끄러짐과 바닥 상태도 실제 이동량을 바꾼다
- 푹신한 바닥에서는 바퀴가 눌려 실효 반지름이 작아질 수 있다
- 오늘 실제 이동 거리는 바퀴 기록의 약 75%였다
- 실효 반지름은 약 0.025 m로 추정했고 설정값은 0.033 m였다
- 엔코더 기록은 바퀴가 돈 양이지 바닥에서 전진한 양을 직접 재는 값이 아니다
- 바퀴가 헛도는 현상은 토크 부족보다 접지와 마찰 부족일 수 있다
- 토크나 속도를 올리면 접지 부족 상황에서 미끄러짐이 더 커질 수 있다
- 캐스터, 무게 배분, 타이어 상태를 함께 살펴야 한다
- SLAM 보정을 짧은 주기로 하면 짧은 구간에서는 오도메트리를 활용할 수 있다

## 플래너와 제어 운영
- 도착 허용오차는 위치 추정 오차와 제어 동작을 함께 고려해야 한다
- 3 cm 허용오차는 실제 위치 오차보다 작았다
- 목표를 지나친 뒤 180° 돌아오는 동작이 생기며 진동했다
- 허용오차를 10 cm로 바꾸자 이 조건에 맞출 수 있었다
- 장애물 부풀림 반경은 로봇 반경 0.21 m와 여유 0.03 m를 더해 계산했다
- 이 부풀림 때문에 벽에서 0.27 m 안쪽인 목표는 경로가 없다고 판단될 수 있다
- 벽 가까운 목표가 실패하면 목표 좌표와 장애물 부풀림 반경을 같이 확인한다
- 플래너가 Fault 상태가 되면 RESET이 필요하다
- stamp가 같은 목표는 중복 목표로 무시된다
- 목표를 촘촘한 웨이포인트로 나누면 매 지점마다 멈출 수 있다
- 코너를 중심으로 웨이포인트를 두고 실행 제한을 상향했다
- 제한을 조정할 때는 목표 도달과 안전한 동작을 함께 관찰한다

## 오늘의 디버깅 습관
- 추측보다 측정을 먼저 한다
- 설정값과 센서 원본 데이터를 대조한다
- 한 번에 하나씩 바꾸고 결과를 비교한다
- 분산 실행 전 컴퓨터 시계를 확인한다
- 로그에 어떤 입력이 왜 탈락했는지 남긴다

## 오늘의 결과와 남은 질문
- 분산 구성의 Wi-Fi 탐색과 시계 문제는 한 Jetson에서 모든 노드를 실행하면 대부분 사라질 수 있다
- 다만 로봇별 IMU 방향, 바퀴 반지름과 간격, LiDAR 포트 보정은 계속 필요하다
- 도착 허용오차와 접지 문제도 계산 장치를 한 대로 합쳐도 남는다
- 실제 경기장을 한 바퀴, 약 10 m 완주했다
- SLAM 지도는 도면 크기 4464×3212 mm와 몇 cm 내로 일치했다
- 첫 코너에서 반대로 265° 회전한 원인은 아직 확인하지 못했다
- 지도 결과가 맞더라도 순간적인 제어 이상 원인은 별도로 추적해야 한다
